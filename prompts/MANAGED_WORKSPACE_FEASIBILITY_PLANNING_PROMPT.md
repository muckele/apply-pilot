# Apply Pilot — H0 Managed-Workspace Feasibility Planning Prompt

Model: GPT-5.6 Sol, if available; report the actual setting.
Reasoning: Max.
Window: Brand-new H0 architecture-planning window, not an active code-repair window.

## Task

Produce a source-led implementation proposal for the preferred web-first Managed Application Workspace. This is **planning only**. Do not implement, install product dependencies, create accounts/credentials, spend funds, start cloud sessions, expose local tunnels, deploy fixtures, access employer forms, mutate databases, create worktrees/branches, stage, commit, push or deploy.

Read current AGENTS files, roadmap/state/decisions, managed-workspace architecture, provider evaluation, Multi-ATS matrix, release gates, and research sources. Inspect the actual local repository and report its state; do not assume an old SHA is the current task base or overwrite existing multi-ATS work.

## Required outcome

Recommend the smallest H1 synthetic probe that can establish whether the accepted local engine can become a no-download, cross-browser public workspace without weakening current authority. The current local companion stays available. No required extension and no new agent Submit command.

## Inspect source

Read actual browser runtime, companion, coordinator, protected session/world, bridge, form correlation, packet/Fill policy, completion UI, accepted synthetic E2E, cleanup utilities, auth, database guards, current extension inventory and deployment topology. Identify what is reusable versus genuinely new. Do not treat a test launcher seam as a production provider integration without review.

## Compare delivery options

Compare vendor-hosted browsers, an owned isolated worker, and local companion fallback. Browserbase and Browserless are candidates, not preselected providers. Verify current public API facts and pricing relevant to the proposal using primary docs. Identify protocol/version, routing, isolated world, page/context ownership, human viewer scope, revocation, recording/logging/persistence, termination/status, maximum session lifetime, file/auth interaction, and support limitations.

Do not enable or recommend CAPTCHA evasion, stealth workarounds, or use employer APIs without proper authority. Do not assume a hosted browser sees localhost on the developer's machine.

## Critical design questions

1. How will the exact accepted protected execution path run remotely?
2. How will owner/run/session/page mapping and short-lived viewer access be enforced?
3. Can direct provider links be revoked or identity-bound, not merely hidden by our UI?
4. How will human input be enabled only after agent writes are fenced off?
5. How will confirmation navigation work without granting arbitrary agent navigation?
6. Which current workflow state is durable across client/worker/provider failure?
7. How will ambiguous create/terminate/mutation outcomes be reconciled without duplicates?
8. What actual sensitive data reaches which service, with recording/logging/persistence controls?
9. Which file/auth/manual cases are required, deferred, or separate scope decisions?
10. What synthetic fixture/control topology avoids remote destructive DB work or unauthorized exposure?
11. What evidence is needed for desktop Safari/Firefox/Chrome/Edge and accessibility claims?
12. What is the bounded experiment cost, including dwell time and failed sessions?

## Required H1 proposal

Specify exact allowed files, interfaces to inspect/change, frozen authority, synthetic-only environment, minimum credentials and who provisions them, explicit spend ceiling proposal, protocol/privacy/ownership test matrix, cleanup and cost reconciliation, failure artifacts without secrets, and stop/go criteria. H1 must fit one reviewable experiment; do not build a distributed platform or active multi-vendor failover.

Do not estimate cost from token usage alone. Do not hardcode historical test counts as future expected counts. Distinguish vendor-documented, source-observed, inferred and unverified behavior.

## Return

Model/Reasoning/Window; actual repository state; reuse map; option comparison; recommended architecture with unresolved decisions; human/agent authority table; dataflow/privacy/recording plan; topology; lifecycle/cleanup/recovery; browser/accessibility matrix; provider evidence and gaps; exact H1 files/tests/budget proposal; current stop conditions; and one next authorization request for the specific synthetic probe if needed.

End with one of:
`H0 PLAN READY — SYNTHETIC PROBE REQUIRES EXPLICIT ENVIRONMENT AND BUDGET APPROVAL`
or
`H0 BLOCKED — <specific unresolved architecture or access requirement>`.

Do not begin H1 in this turn.
