# P0.2 human completion boundary — design for owner decision

Status: design and local synthetic feasibility only, 2026-09-22. Base: reviewed P0.1 `0aae75394015aa6051d8b28ed5a1b8bda8a84bb6`. No browser-policy or production implementation change is made here. All new pages, values, and HTTP receipts are synthetic. This document does not establish live ATS compatibility.

## Decision

Approve **an explicit, irreversible human-only handoff** as the later implementation direction, conditional on proving an operation fence and separate owner/employer browser contexts in integrated tests. Both are hard release gates. Until that proof exists, retain the current safe stop and offer an explicit manual fallback in an ordinary browser. A general same-origin or confirmation-path exception while automation remains active is rejected. The prototype proves only that a protected session can close without closing its page; it does not prove the coordinator can safely retain that page while a Fill, route callback, CDP operation, or bridge invocation remains pending.

## Current behavior and evidence boundary

The current command grammar is `GET_STATUS`, `OPEN_TARGET`, `INSPECT_FORM`, `FILL_APPROVED_FIELDS`, `CLOSE_WORKFLOW` (`lib/application-browser/types.ts`). The control binding is installed on the exact owner control page and checks page, main frame, origin, path, run ID, and bridge generation (`control-bridge.ts`). The employer page receives no command binding. `CLOSE_WORKFLOW` closes owned resources and the nonpersistent browser context; it cannot be reinterpreted as handoff.

The target controller creates the protected session and page, then installs a main-frame document route (`coordinator.ts`, `createPlaywrightTargetController`). In `STEADY_TARGET`, the route requires the canonical frozen URL. A changed URL is aborted with `blockedbyclient` and `TARGET_NAVIGATION_BLOCKED` is reported before that **navigation request** leaves Chromium. Non-navigation requests are continued. A separate `framenavigated` check detects postnavigation drift. The companion's unsafe callback safe-stops and closes the workflow. A blocked `/confirmation` URL alone does not identify whether a prior POST reached an employer: an off-target original POST is blocked at that first request, while a same-target POST can pass the URL guard and a subsequent redirect can be blocked. Neither case proves employer acceptance.

Fresh rerun of the reviewed P0.1 case: a separate HUMAN test actor fired the in-place submit event and displayed synthetic confirmation; a subsequent GET `/confirmation` was blocked while the page remained at `/apply`. The P0.1 characterization also observed three page-owned fetch/XHR/beacon attempts on Fill, locally route-fulfilled only. A new production POST instrumentation attempt was stopped after two failed page-context observation attempts; it supplies no collector-receipt conclusion. The exact guard ordering above is source evidence, not a new network receipt.

The opt-in P0.2 probe uses Playwright 1.62.1 and a local loopback HTTP server. It observed a script-scheduled POST `/invalid` returning validation status, a separate HUMAN POST `/apply` received by the local collector followed by a 303 and completed `/confirmation` navigation, an unrelated same-origin navigation, and an aborted external popup request. This is browser/prototype feasibility, not behavior under the production target guard. Directly closing a test-owned `ProtectedApplicationBrowserSession` rejected subsequent protected calls while leaving synthetic input values in the page. Its `close()` invalidates local authority synchronously but dispatches disposal, operation settlement, script removal, object-group release, and CDP detach as best-effort background work. This direct-session test does not prove settled pending writes or safe production handoff.

The server run state is separate from browser state. Guarded Fill consumes one permanent server attempt; `READY_FOR_USER_SUBMISSION` is a durable run state and `COMPLETED_BY_USER` is reached through the owner's explicit attestation API. Neither a browser handoff nor a confirmation URL completes the run. Current control copy says Fill requires explicit action and personal submission requires human confirmation, but lacks an explicit **before-Fill** warning that page script can transmit entered values before Submit.

## Alternatives

| Choice | Authority and state | No companion Submit and navigation coverage | Cleanup and user effort | Decision |
| --- | --- | --- | --- | --- |
| A. Irreversible handoff | Retire inspection/Fill and bridge operation authority, retain only exact-owned lifecycle/status supervision; keep filled page if quiescence and context isolation are proved | No new employer action API. Human may navigate or submit after the fence; cross-origin and scripts remain untrusted, not proof of human action | Same-page work survives while the disposable browser lives; visible 60-minute limit and close required | Preferred implementation direction, conditional on integrated fence and isolation proof |
| B. Confirmation exception with automation retained | Keeps protected session/bridge capable of future work while allowing selected navigation | Form actions, redirects, validation returns, script navigation, popups, and unrelated same-origin paths cannot be safely classified by URL substring, same origin, selector, click timing, or `isTrusted` alone | Retains ambiguous authority and destination policy | Reject for P0.2 |
| C. Manual browser fallback | Close disposable context and give the target URL and manual instructions; no state or cookie transfer | Current no-submit boundary remains, but values must be reentered and uncertain prior submissions must not be retried | Highest human effort, known loss of unsent values | Explicit fallback when A cannot fence or fails safely |

No destination URL from React, a model, or employer DOM authorizes automation. After A completes, subsequent navigation may be a **human action or untrusted page-script effect**; the companion does not distinguish them or infer submission. It does not inspect, click, type, submit, or classify the destination. Existing host and frozen-target policy stays active until the irreversible transition finishes. The proposed post-fence policy permits main-frame HTTPS navigation in the **isolated employer context** for human completion, including redirects, but blocks navigation to the configured Apply Pilot origin and loopback/private-network origins. It never grants an automation target or privileged binding at the destination. HTTP beyond loopback is unsupported. Unexpected popup/new page attempts are closed and terminate the handoff as unsafe; popup-dependent completion uses C. This is a proposed browser policy requiring owner approval and integrated tests, not current behavior. It cannot promise that employer scripts will not navigate or transmit. If required human completion needs an unsupported destination, popup, or employer login, use C rather than an ad hoc exception.

Do not yet relax navigation. |
| `TARGET_OPEN`, Fill finalized | Same request after authoritative final Fill status and no active operation | `HANDOFF_PENDING` | Same gate. Server's consumed attempt remains consumed. |

| `HUMAN_ONLY` | Exact owner invokes `END_HUMAN_SESSION`, or 60 minutes elapse from confirmed handoff | `CLOSED`/`ERROR` | Idempotent close; revoke first and attempt exact-owned page/context/browser cleanup. Show a 10-minute and 2-minute warning before expiry while control is trusted. No extension in this version; the 60-minute hard limit is disclosed before handoff even if unsent work may be lost. |
| Any state | Browser crash or cleanup failure | `ERROR` or terminal unknown | Revoke first; attempt bounded exact-owned cleanup and record `HUMAN_SESSION_CLEANUP_UNCERTAIN` if closure cannot be verified. Never report the employer page closed or employer submission complete merely because cleanup timed out. No unowned process kill. |

The exact later interface proposal is payload-free `HANDOFF_TO_HUMAN` and `END_HUMAN_SESSION` commands, `HANDOFF_PENDING` and `HUMAN_ONLY` browser-local status, and terminal `HUMAN_SESSION_CLEANUP_UNCERTAIN` error reporting. These are proposals for owner approval. Preserve `CLOSE_WORKFLOW` semantics as context-destroying at every stage; `END_HUMAN_SESSION` is the named human-session close action. Both new commands must be admitted only from the original exact owner control page for the immutable run; repeated handoff/close calls are idempotent while that bridge remains valid. No generic employer control or destination parameter is accepted. A refresh/back invalidates that bridge and closes the human session, rather than rebinding a new page. The server's existing Fill attempt identity and durable status remain authoritative for replay prevention. Prefer no schema change; if cross-process durable handoff identity becomes necessary, return for a separate owner decision.

The later implementation must own a real quiescence barrier: track operation promises and route callbacks at their dispatch points, stop new admissions before waiting, wait for authoritative completion or abort exact-owned resources, and verify CDP cleanup before changing navigation policy. A timeout is an escalation to safe stop, not proof of quiescence. The current protected-session `close()` intentionally uses best-effort background cleanup, so simply awaiting it is insufficient for this gate. A controller-level primitive must prevent any late write, listener, route callback, or stale captured handle from acting after the state switch. Keep a strict exact-target guard throughout pending teardown. If the page cannot be safely retained with this proof, close it and offer C.

The current control and employer pages share one nonpersistent context, so the page-scoped binding check alone does **not** prove that navigation toward Apply Pilot cannot reach ordinary authenticated app capabilities. Same-page A is blocked until the later implementation creates separate control and employer contexts **from initial target open**, before any Fill, and tests owner-origin isolation. The employer context must never receive Apply Pilot authentication; it must block navigation toward the configured Apply Pilot origin and loopback/private origins even after handoff, and close unexpected popups/new pages. It must not migrate a filled page between contexts, attach to a personal profile, or copy cookies/storage. Handoff also preserves exact control-route and page-scoped bridge checks, and control trust loss closes the employer context. The disposable employer browser/context/page remain exact-owned and visible while alive. The 60-minute maximum begins only after confirmed handoff, is displayed before the user's irreversible confirmation, counts down continuously, warns at 10 and 2 minutes, has no extension, and may close during unfinished manual work at expiry. The owner can use `END_HUMAN_SESSION` earlier. No storageState export, cookie copy, hidden-field capture, or profile persistence.

## User-facing sequence and uncertainty

1. **Before live Fill activation:** show and require acknowledgement: “Filling a field can trigger the employer page's own scripts. Values may be sent to the employer or third parties before you press Submit. Apply Pilot will not press Submit, and it cannot promise that filling is network-free.” This must sit at the Fill decision, not only at handoff. The local intercepted P0.1 requests do not demonstrate isolation in a live page.
2. After Fill, show authoritative attempt status, fields requiring manual work, and “Review the entire employer form.” If result is unresolved, say “Fill outcome is uncertain; do not repeat Fill.” Do not offer handoff until the fence gate is satisfied.
3. Offer a separate “Finish manually in this browser” action with an irreversible warning: automation and inspection end for this workflow; the disposable browser retains the page for at most 60 minutes, with warnings at 10 and 2 minutes remaining and no extension; employer scripts can still transmit or navigate; refreshing, leaving, or closing the Apply Pilot control page ends this browser session and may lose unsent values. The user explicitly confirms.
4. In `HUMAN_ONLY`, show only lifecycle/status, countdown, and “End human session.” The user completes manual fields and chooses employer Submit. A URL or success-looking page is not an attestation. Validation errors and manual edits are the user's responsibility. Employer-page refresh/back may lose unsent values and never reactivates Fill. Control-page refresh/back closes the owned employer context; reconnect or a new tab cannot restore it.
5. The existing two-step owner attestation remains separate: only after the user personally submitted may they choose “I personally submitted this application.” It records their statement, not employer-confirmed delivery. If the browser, network, or response leaves submission uncertain, instruct the user to inspect the employer site's own status or contact the employer before any retry. Never auto-resubmit. Cancellation leaves the run uncompleted.
6. If same-page handoff is unavailable, explicitly close the disposable workflow and offer manual reentry at the known target URL in the user's ordinary browser. Do not transfer cookies, hidden values, unsent form state, or an opaque session; warn that reentry is required and an uncertain prior submission must be checked first.

## Later implementation surface and required tests

Required, subject to owner approval: `lib/application-browser/types.ts` (exact command/status grammar), `lib/application-browser/control-bridge.ts` (admission and stale-generation rules), `lib/application-browser/coordinator.ts` (state, operation fence, target guard transition, page ownership), `lib/application-browser/protected-browser-session.ts` (verified retirement primitive if feasible), `lib/application-browser/browser-runtime.ts` and `scripts/application-browser-companion.ts` (separate contexts from initial target open, 60-minute lifetime, exact-owned cleanup), `components/application-browser-control.tsx` (pre-Fill disclosure, handoff, uncertainty, countdown), and browser safety tests. Preserve the existing user attestation route and service unless a proved gap requires an owner-approved change. No provider adapter, dependency, schema, or source eligibility expansion is proposed.

Acceptance must demonstrate: no companion submit/click/evaluate surface; exact-target guard during automation and pending handoff; original POST versus redirect receipts at an exact-owned collector; pre-Fill disclosure acknowledged; pending Fill/inspection/CDP/route callback cannot cross the authority switch; interrupted cleanup fails closed; stale and duplicate bridge calls cannot restore inspection or Fill; control refresh/back/close closes the employer context; another tab/process cannot attach; same-page values survive only after proved teardown; employer redirect, validation return, unrelated same-origin path, script-timed navigation, popup, cross-origin attempt, and navigation toward Apply Pilot obey the explicit post-fence policy without privileged capability; separate contexts prove no owner cookies/binding in the employer context; 60-minute countdown, warnings, expiry, idempotent `END_HUMAN_SESSION`, and uncertain cleanup are observable; attestation still requires a separate owner action and never derives from URL. Each test must record whether a request was attempted, intercepted, locally received, responded to, and navigated, without claiming live delivery.
