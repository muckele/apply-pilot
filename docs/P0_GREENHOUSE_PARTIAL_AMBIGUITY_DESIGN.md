# Safe partial normalization for ambiguous duplicate fields

**Design only. Recommendation: A, quarantined ambiguity groups. Implementation requires Mathew's explicit authorization.** This design is based on released `origin/main` `113d04c958ff0405f14d75a0eedea8afd74e42c0` (tree `c7f39fba97799c0b680f7f90354c3d9e3f53892f`). It changes no production behavior, schema, test, employer page, or applicant data.

## 1. Verified current behavior and source trace

The protected browser world's `extract()` produces a bounded report and opaque candidate. `protected-browser-session.ts` parses the report, creates one opaque field slot per source coordinate, and retains the full candidate for later verification (`extractApplicationForm`, around lines 1011–1140). `form-inspection-controller.ts` waits for stability, extracts, correlates, verifies the candidate against a fresh report, then exposes only a generation facade (around 630–720). The controller repeats candidate and normalized-report verification before a write (around 760–830).

`form-inspection.ts` classifies and normalizes every report field first (around 882–980). `deriveNormalizedFieldKey` hashes form title, section heading, field type, and either semantic key or canonical question (around 780–791). A global `seenFieldKeys` pass then throws `AMBIGUOUS_DUPLICATE_FIELD` before section/form keys or any snapshot are built (around 985–1029). The current section key hashes its sorted field-key list and heading; the form key hashes sorted section keys and title; the form fingerprint hashes sorted field fingerprints, form structure, apply host, and versions (around 825–849 and 997–1029). Stored-snapshot parsing independently rejects duplicate keys and recomputes field, section, form, and form fingerprints (around 1127–1289).

Uniqueness is an authority invariant, not merely a presentation preference. `form-inspection-correlation.ts` builds a key-to-field map, rejects repeated keys, correlates each raw slot through a one-field normalization, requires every writable normalized field to receive exactly one binding, and seals those bindings (around 151–316). The protected session rejects duplicate binding keys, fingerprints, or source coordinates (`protected-browser-session.ts`, around 358–412); the protected browser world seals only validated bindings against the **whole** live candidate graph and writes only a sealed key/fingerprint/type whose original control is still current (`protected-browser-world.ts`, around 2114–2400). It does not require a binding for every extracted control.

`answer-packet-service.ts` publishes a verified snapshot and packet together, flattens every normalized field into one packet answer row, requires the row set to equal the field set, and uses a map keyed by `normalizedFieldKey` (around 331–332, 534–603, 1003–1085, 1150–1220, 1300–1390). `answer-packet-domain.ts` requires unique packet keys and exact option-validation context; its summary currently rejects an empty answer set and counts manual work from answer rows only (around 610–620, 768–810, 975–1058). `service.ts` checks packet hash, version, reviewed state, and summary readiness when resolving review (around 840–930). `fill-attempt.ts` verifies owner/run/inspection/packet pointers, review, answer rows, field fingerprints, and proposal hashes; it rejects an empty eligible set before the one-attempt state transition (around 300–420 and 630–730). `form-inspection-controller.ts` also requires acquired writes to match its accepted generation and normalized field map (around 455–535, 835–910). `fill-orchestration.ts` forwards only acquired eligible fields, while the protected writer preserves occupied values and never submits. The current UI/API summary schemas and copy live in `answer-packet-api.ts` and `control-presentation.ts`.

Consequently a partial snapshot cannot be created by merely suppressing the duplicate exception. The parser, correlation, packet-row coverage, summary, review presentation, and Fill boundary all assume that every represented field has a unique key and that packet rows describe all represented fields.

## 2. Evidence and alternatives

The final P0.3 GH1 receipt found **two collision groups with four total members**: one semantic-key collision between structurally different controls and one identical-key file-control pair with no approved distinguishing feature. It did not establish a stable, reorder-safe identity for either pair. Batch 2 GH3 and GH4 each loaded one visible native form and stopped on the same protected duplicate error; their collision cardinalities and layouts were not retained. Thus three of three observed Greenhouse forms in this sample yielded **zero normalized snapshots**, despite visible forms. This is a bounded sample, not a provider-wide rate or support claim. See the read-only P0.3 worktree's `docs/P0_3_GH_FINAL_EVIDENCE.md` and `docs/P0_3_BATCH_2_READ_ONLY_INSPECTION_RESULTS.md` at checkpoint `61435daa033410a5d8ead3aeaeb6fd9d097b29c8`.

| Approach | Benefit | Decisive cost or limit |
|---|---|---|
| **A. Quarantine whole collision groups** | Unique fields can retain their existing keys and ordinary review path. Every colliding member remains anonymous, non-writable, and counted as manual work. | Requires a versioned snapshot, complete collision accounting in correlation, packet summary/presentation changes, and empty-unique-field handling. Freshness must bind the anonymous members. |
| **B. Expand field-key disambiguation** | Could make more fields individually addressable. | GH1's identical file pair has no approved stable discriminator. Ordinals, DOM IDs, raw names, and render order would transfer authority after reorder or replacement. The differing semantic-key pair also lacks a proved stable rule. Reject B. |
| **C. Keep whole-form fail-closed** | Retains today's simple, strong guarantee: no answer authority survives any duplicate collision. No code or migration work. | In the three observed Greenhouse cases, zero normalized snapshots or published classification results survived the duplicate throw, including results for any otherwise unique fields; their number is unknown. Internal per-field normalization and classification did run before the throw. It cannot offer safe partial assistance on those pages. |

Recommend **A**, with C as the mandatory fallback if any acceptance gate below fails. A never assigns an identity to a duplicate member. A Greenhouse-specific adapter is unjustified: the evidence shows a generic key-collision condition, not a stable provider-specific relationship or a safe DOM rule. The design applies to any protected report with duplicate normalized keys; it does not claim general Greenhouse support.

## 3. Exact v2 snapshot and integrity contract

Build all normalized *internal* field material as today, under the existing report limits (four forms, 32 sections per form, 200 total fields, 1,000 total choices). Partition by `normalizedFieldKey` **globally across the report**. A key appearing once yields an ordinary `NormalizedApplicationFormField` in `section.fields`; its key derivation is unchanged. A key appearing two or more times yields **no** ordinary field for any member. No arbitrary member, including a member otherwise classified `PROPOSABLE`, survives. Collision grouping precedes any answer-source lookup or writer binding.

The persisted v2 snapshot is a strict, tagged shape: `schemaVersion: 2`, `normalizerVersion: 2`, current classifier version, `fingerprintVersion: 2`, `forms`, and `ambiguityGroups`. Each section has its current `fields` array (now allowed to be empty) plus `ambiguousMembers`. Each anonymous member record contains exactly `{ collisionKey, memberIntegrityDigest, required }`; it has **no** `normalizedFieldKey`, field fingerprint, semantic key, proposal, answer source, source coordinate, writable reference, or display question. The top-level `ambiguityGroups` array contains exactly `{ collisionKey, memberCount, requiredMemberCount, groupFingerprint }`. The `collisionKey` is the would-be normalized key but is typed and named only as a **group** identifier; it is never a packet answer key or writer target. A group is global because today's collision check is global and equal headings/titles can collide across sections or forms. Its anonymous member records remain in their original section solely to bind section/form integrity. No raw employer wording, choice label, help text, value, DOM ID/name, selector, ordinal, or control reference is persisted for these members.

At build time, compute each `memberIntegrityDigest = H("application-form-ambiguous-member:v2", canonical **full pre-collapse report** material, including the collision key, form/section comparison text, question/help comparison text, original and normalized field type, **raw and normalized unsupported reason**, classifier/disposition facts, requiredness, autocomplete, constraints, and the sorted multiset of all canonical choice labels/disabled states)`. Retain duplicate choices in this *hash input* even when today's field normalizer marks the control unsupported and clears its normalized choices. Otherwise two materially different duplicate selects could have the same group commitment. Preserve the raw unsupported reason because several raw reasons can collapse to one generic disposition reason. This is an integrity commitment, **not a member identity**. Persist only the digest and required flag. Equal members may have equal digests; multiplicity must be preserved. `groupFingerprint = H("application-form-ambiguity-group:v2", collisionKey, memberCount, requiredMemberCount, sorted multiset of member digests)`; sorting preserves duplicates. The section key uses a v2 domain and hashes its canonical heading, sorted unique field keys, and sorted multiset of its anonymous `{collisionKey, memberIntegrityDigest, required}` records. The form key uses a v2 domain and hashes title plus sorted section keys. The v2 form fingerprint uses a distinct domain and hashes authoritative apply host, all versions, sorted forms with unique field fingerprints and anonymous section commitments, and sorted group fingerprints. It must never reuse the v1 form-fingerprint domain.

Canonical verification requires: total unique fields plus anonymous member occurrences equals the bounded source field count at build/correlation; every `ambiguityGroups` entry has at least two occurrences; each anonymous occurrence belongs to exactly one declared group; group counts and required counts equal the occurrences; no unique field key equals any collision key; unique fields and groups are strictly sorted; anonymous occurrence arrays are sorted nondecreasing by the complete tuple and may repeat; v2 section/form/group/final fingerprints recompute exactly. Identical section or form keys that cannot be canonically distinguished remain a whole-inspection stop. The live builder recomputes member digests from the protected report. A stored snapshot parser can verify their hash shape, multiplicity, canonical structure and all enclosing commitments, but cannot recover the original raw material from a digest. Fresh candidate verification recomputes from a new protected report before publication or write; the existing whole-graph `sameGraph` check remains the live reference authority. A forged database row with both JSON and stored fingerprint changed is outside the current database trust model, as it is for v1.

`fieldCount` at the protected inspection boundary remains total observed controls. Add explicit `uniqueFieldCount`, `ambiguousQuestionCount = sum(memberCount)`, and `ambiguousRequiredCount` to the correlated/publication result; do not silently redefine a count. In the packet summary, retain `fieldCount` as the number of ordinary answer rows, and add the two ambiguity counts plus `observedFieldCount = fieldCount + ambiguousQuestionCount`. The existing `manualRequiredCount` must include ambiguous required controls, while the separate ambiguity counts make that total intelligible. Never infer semantic meaning or actual employer validation from the `required` flag.

Legacy v1 snapshots and packets remain parsed and verified with their exact v1 rules and fingerprint domain. New inspections emit v2; they do not reinterpret stored v1 hashes. A first v2 inspection may replace a v1 packet even when visible unique fields look the same. The packet projection shape can remain unchanged: its `formFingerprint` binds the v2 ambiguity structure, while its `answers` contain **only unique fields**. New packets use a bumped builder version so the empty-answer rule and summary meaning are explicit. An empty answer array is allowed **only** with a verified v2 snapshot containing at least one ambiguity group and zero unique fields; it creates zero answer rows, no reviewable proposal, and no Fill eligibility. Other empty packets remain invalid.

The empty-answer exception requires a **verified inspection witness**, not a client count. Define an internal `derivePacketInspectionContext({ authoritativeApplyHost, expectedFormFingerprint, snapshot })` that calls `verifyNormalizedApplicationFormSnapshot`, then returns the exact unique-field key set, `schemaVersion`, `formFingerprint`, `ambiguousQuestionCount`, and `ambiguousRequiredCount`. `buildCandidatePacket` derives it from the fresh protected report's verified snapshot; `loadVerifiedCurrentAnswerPacketForLockedRunInTransaction` derives it from the stored snapshot and authoritative run host; packet rebuild derives it again before constructing a new packet; and run-review/Fill use only that verified current-packet loader. `packetProjectionFromRows` must require rows to cover **exactly** the context's unique-field keys. `summarizeApplicationAnswerPacket` must receive this internal context and accept zero answers/rows only when builder version 2, context schema version 2, context ambiguity count is positive, context unique-field count is zero, and packet/context form fingerprints match. The service must derive public ambiguity and manual-required counts from this verified context on **every** packet read, never trust persisted summary text or a client count. A standalone empty projection may be structurally parseable for hashing, but cannot become a valid current packet or ready summary without this witness. The public API does not accept a witness from the browser, and no group digest or count becomes an answer row. The published packet and inspection must still be created atomically under the existing owner, target, policy and version fences. The JSON snapshot and integer version columns already exist in `ApplicationRunFormInspection`; packet versions and answer rows also exist. **No SQL/Prisma schema migration is required.** This conclusion depends on the bounded v2 JSON shape and zero-row packet being accepted by the application service; it is not an assumption that v1 parsers already accept them.

## 4. Freshness, review, and writer authority

For every protected source slot, correlation first verifies the complete opaque source graph. It computes the would-be key and integrity digest and exhaustively accounts for that slot in exactly one bucket: one unique normalized field or one anonymous occurrence of a declared collision group. A missing, extra, mismatched, or differently grouped slot aborts the **whole** inspection. It then builds writer bindings only for unique normalized fields that satisfy the existing writable-type rules; it explicitly skips every group member, even when that member's control type would be writable or its isolated classification would be proposable. Expected binding coverage is measured over unique writable fields only. The protected world may seal this subset, but it still verifies the whole graph and allows writes only to sealed keys. The controller must also reject any acquired key absent from the unique-field set, present as a collision key, or not `PROPOSABLE`; server packet construction and Fill acquisition independently use only verified unique fields and reviewed proposals. Group objects never enter answer rows, source lookups, review mutations, eligible Fill candidates, step keys, or writer bindings.

A material anonymous-member change, group cardinality change, conditional insertion/removal, section/form relocation, or transition between unique and ambiguous changes the v2 section/form fingerprint and therefore the packet hash/freshness fence. Reorder of equivalent members or sections leaves the canonical fingerprint unchanged. A same-looking **control or option** replacement may have the same structural digest; **the digest is not an identity proof**. The protected candidate's whole-graph object comparison already rejects a replaced control or option, including an ambiguous one (`protected-browser-world.ts`, `sameGraph`). It must invalidate that accepted generation, set browser packet trust to stale/reinspection required, and prevent writing. A same-looking replacement of a label dependency while its associated control stays put is currently allowed by some protected-world tests; it is semantically equivalent under the present report contract and is not a member-control replacement. If a later implementation treats dependency-object replacement itself as a freshness event, that needs an explicit protected-world change and tests, not an assertion that the current guard catches it. Disable exact replay for **every** v2 inspection containing an ambiguity group: each new publication creates a new inspection and packet version, even when the structural form fingerprint is equal. This rule needs no untrusted client claim about why reinspection occurred, and prevents a post-replacement publication from reviving the previously reviewed packet. Before reinspection, the persisted packet can remain stored, but it is not actionable for protected Fill without a current accepted candidate. The design therefore treats actionable freshness as the conjunction of verified stored packet/version/hash, current browser generation, whole-graph candidate verification, and exact target. Any failure closes authority; no optimistic partial write is permitted.

Review readiness means **all proposals for unique fields have been reviewed**, not that all employer questions are complete. `contracts.ts` must add a bounded `acknowledgedAmbiguousQuestionCount` to the resolve-review request: require it for v2 partial packets, allow omitted/zero only for legacy v1, and never let the client supply the authoritative count. `control-presentation.ts` must construct the exact request field, and the API parser must reject extra or malformed count data. `service.ts` must compare it to the count from the verified current inspection context in the same owner/run/packet-hash transaction before setting `reviewedAt` or resolving the run. `components/application-browser-control.tsx` must show the count and manual-work sentence beside the review confirmation, send the exact displayed count, and refuse a stale or mismatched acknowledgment. A zero-unique packet may be acknowledged for manual completion, but never enables Fill. After a successful partial Fill, the terminal state and handoff copy must continue to say that `N ambiguous employer questions require manual completion`; no completed-Fill message may imply submission or whole-form completion. Existing exact-target, owner-isolation, one-attempt Fill, occupied-value preservation, uncertainty recovery, and Human-Submit fences stay in force. The emitter of a candidate invalidation and UI must mark packet freshness stale immediately; the server must not accept a replay of a v2 partial snapshot to erase that stale state.

| Owner-facing state | Required conceptual message and action |
|---|---|
| Unique safe fields available for review | “Review the proposed answers for the fields Apply Pilot could identify safely.” Show only unique-field answer rows. |
| Ambiguity alongside unique fields | “N ambiguous employer questions require manual completion.” Show the verified occurrence count separately from ordinary manual/unsupported rows; do not show inferred meaning or an approval control for group members. |
| No eligible fields, ambiguity present | “Apply Pilot has no fields it can fill on this form. N ambiguous employer questions require manual completion.” Offer manual completion/human handoff, no Fill activation. |
| Candidate or packet stale | “The employer form changed. Reinspect and review a new packet before Fill.” Disable proposals and Fill against the old generation. |
| Ambiguity changes after review | Show the same stale/reinspect state, with prior approvals visibly inactive; a fresh packet version requires a fresh review even if the unique questions look unchanged. |
| Fill finalized for unique fields | “Fill finished for the approved fields only. N ambiguous employer questions still require manual completion. You submit the employer form yourself.” Preserve existing uncertainty wording when a write outcome is unknown. |

## 5. Threat model and required RED/GREEN tests

| Threat / acceptance scenario | Required safe result | Owning suites |
|---|---|---|
| Two truly identical duplicate fields plus one unique eligible field; three-member group | Every duplicate occurrence is quarantined; unique field persists; no group key in proposal, packet answer, binding, or write request. | `application-run-form-inspection.test.ts`, `application-browser-form-inspection-correlation.test.ts`, `application-run-answer-packet-domain.test.ts`, `application-run-answer-packet-service.test.ts` |
| Equal normalized key with differing source ordinals; duplicate labels in one or several sections | No ordinal/DOM/name-based disambiguation. One global group, with section occurrence accounting; unaccounted slot fails closed. | normalization and correlation tests |
| GH1-like semantic-key collision between visually different controls, including one otherwise proposable and one manual/excluded; identical file-upload questions | All members quarantined regardless of classification or control family; no source lookup, upload, or writer target. | normalization, packet-service, correlation, protected-session tests |
| Duplicate native selects with different choices | Choice material changes member/group/form integrity; neither select gets a choice key in a packet or a sealed binding. | normalization, correlation, protected browser smoke tests |
| Member or section reorder with equivalent material | Canonical multiset, section/form fingerprint and group fingerprint remain equal; no member identity is inferred. | normalization snapshot tests |
| Add/remove a member; change cardinality; conditional insertion/removal; change requiredness/choice/constraint or raw unsupported reason; move across sections | Group/section/form fingerprint changes, reviewed packet is stale, no write. | normalization, packet-service, controller freshness tests |
| Member becomes hidden/visible, or same-looking control/option is replaced | If the extracted graph changes, fingerprint changes; even if material is identical, whole-graph candidate control/option identity invalidates and requires a new packet version before Fill. Unobserved hidden controls grant no authority. Test same-looking label-dependency replacement separately against its existing semantic-equivalence rule. | protected DOM/stability, controller, coordinator/presentation tests |
| Ambiguous group mutates after review; a unique field becomes ambiguous or reverse | Old packet hash/version/generation fails; reinspection and fresh user review are required; no old approval transfers. | packet-service, run-review, Fill-attempt, controller tests |
| Unique eligible field plus ambiguous required controls; occupied existing value | Only reviewed unique target is acquired; writer preserves occupied value; ambiguity count and manual-required count remain visible after Fill. | Fill-attempt, fill-orchestration, protected writer, presentation tests |
| Entire form ambiguous, or forged empty packet without inspection witness | v2 packet has zero answers/rows and positive verified ambiguity count; resolve requires exact manual-work acknowledgment; Fill acquisition returns no eligible fields without starting an attempt. An empty packet with a v1, missing, forged, or mismatched witness fails. | packet-domain/service, run-review, Fill-attempt and presentation tests |
| Malicious collision markup, forged group/packet/counts, duplicate binding, uncertain write | Strict parser/correlation rejects any unmatched count/hash/key; no group authority can be forged; existing no-submit, owner isolation, one-attempt and uncertainty regressions stay green. | parser, correlation, packet, protected browser/no-submit, owner and Fill suites |

Write the RED cases against public domain/service boundaries first, especially group-to-writer leakage, cardinality freshness, empty-unique publication, and same-looking replacement after review. The GREEN implementation must satisfy them without a test-only bypass. Existing v1 snapshot and packet fixtures remain regression controls. No PostgreSQL test is part of this design mission; a later implementation authorization should include the relevant persistence tests.

## 6. Smallest likely implementation surface and remaining evidence

The likely production edits are `lib/application-runs/form-inspection.ts` (v2 shape, canonical verification, fingerprints, counts), `lib/application-browser/form-inspection-correlation.ts` (complete partition proof and subset bindings), `lib/application-browser/form-inspection-controller.ts` (unique/proposable acquired-key guard), `lib/application-runs/answer-packet-service.ts` and `lib/application-runs/answer-packet-domain.ts` (v1/v2 readers, verified witness, no exact replay for partial snapshots, unique-only row coverage, zero-answer case, summary and version handling), `lib/application-runs/answer-packet-api.ts` and `lib/application-browser/control-presentation.ts` (strict public counts and truthful states), `lib/application-runs/contracts.ts` and `lib/application-runs/service.ts` (exact manual-work review acknowledgment), and `components/application-browser-control.tsx` (the actual review summary, confirmation and post-Fill/manual-work text at around line 1690). The coordinator/invalidation path may need a narrow stale-status change; verify with the RED cases. `fill-status-presentation.ts` may need the verified packet ambiguity count passed in, or the component can combine its existing Fill result with the packet summary without changing that status schema. `fill-attempt.ts`, protected session/world, and `fill-orchestration.ts` should need only invariant tests unless those tests expose a gap. The exact affected set is a design estimate, not implementation authorization.

Implementation would prove a generic partial-snapshot mechanism on synthetic cases, not which real Greenhouse fields are safely unique or useful. GH3/GH4 collision structure remains unknown. GH1's two groups still have no safe member identity. Source eligibility, employer validation, dynamic behavior, actual manual burden, and a useful intended applicant trial remain unproved. Lever frame/redirect and Ashby structure observations are separate problems. After implementation, at least one separately authorized Greenhouse read-only reinspection would still be needed before selecting a P0.4 intended trial.
