## Completed milestones

### Milestone 0 — Planning gate

Architecture map, provider/model inventory, gap analysis, threat model, and acceptance criteria were produced and approved before any implementation began.

### Slice A, Commit 1 — Kimi K3 provider and feature-level routing

- `lib/ai/pricing.ts`: `kimi-k3` registered at $3.00 input / $0.30 cached input / $15.00 output (including reasoning) per 1M tokens; pricing remains fail-closed for unregistered models and changes only through intentional code edits.
- `lib/ai/config.ts`: `AI_PROVIDER_OVERRIDES` feature-level routing. Only `APPLICATION_PLAN` is eligible; every other feature stays on the global provider (`gemini`/`openai` only).
- `lib/ai/providers/kimi.ts`: the Kimi K3 request contract — `max_completion_tokens`, top-level `reasoning_effort` (`low` default; `low|high|max` only), strict JSON Schema output; never sends sampling parameters or tools; validates `finish_reason`; fail-closed usage accounting; endpoint hardcoded to `https://api.moonshot.ai/v1`; credential is `MOONSHOT_API_KEY` only.
- Offline coverage: `tests/provider-routing.test.ts`, `tests/kimi-provider.test.ts`.

### Slice A, Commit 2 — Evidence-bound Kimi application planning

- `prompts/applicationPlanPrompt.ts`: job content is untrusted data, never instructions; output is advisory only.
- `lib/ai/application-plan.ts`: `buildApplicationPlanPayload()` constructs a bounded, allowlisted payload snapshot containing two deterministic catalogs:
  - `jobRequirements` — `req-N` / `pref-N` / `tech-N`
  - `evidenceCatalog` — `summary-1`, `skill-N`, `achievement-N`, `work-N`(+`-highlight-M`), `project-N`(+`-highlight-M`), `education-N`, `certification-N`, `profile-skill-N`
- Evidence and requirement IDs are generated by the local builder from position/order — never by the model. IDs are local to the immutable planner payload snapshot and are designed for later reuse by ApplicationRunAnswer and browser-field provenance.
- The provider output references `requirementId`/`evidenceIds` only. `enforceApplicationPlanEvidence()` drops and records unknown requirement IDs, removes and records unknown evidence IDs, deduplicates repeated IDs, forces `gap=true` when no valid evidence remains, removes citations of do-not-exaggerate skills, and discloses numbers in free-text fields that are absent from the evidence catalog.
- Human-readable requirement/evidence text in a returned plan is hydrated from the catalogs only. Provider-produced text is never the source of truth for provenance.
- The deterministic local fallback composes its evidence map from the catalogs and is evidence-valid by construction.
- Plans remain advisory data: `planApplication()` never executes code, invokes tools, fills forms, sends messages, or submits applications. Provider/model/promptVersion/requestHash/usage provenance is preserved on every plan.
- Privacy minimization by construction: no contact details, raw resume text, file bytes or paths, Answer Vault content, EEO/demographic/disability/veteran/criminal-history data, work-authorization notes, cookies, session or browser state, or hidden page content. Projects, education, and certifications are included only in compact bounded form. Payload bounds keep the worst case under the 12,000-token `APPLICATION_PLAN` policy.
- Offline coverage: `tests/application-plan.test.ts`.

## Evaluation

One runner only: `npm run ai:evaluate` (`evaluation/ai-provider-evaluation.ts`).

- `AI_EVAL_PLAN_TOP` defaults to `0`: zero live planning calls.
- `KIMI_EVAL_MODE`: `synthetic` (default; built-in fictional fixture, no user data), `sanitized`, or `real`. `real` additionally requires `KIMI_EVAL_DATA_ACKNOWLEDGED=true` and transmits privacy-minimized resume/job data to Moonshot — an explicit data-sharing decision by the operator.
- Gating sequence: mocked tests → synthetic fixtures → one sanitized live smoke test after explicit approval → one approved real-job comparison → larger evaluation only after earlier results are reviewed.
- Reports write to the gitignored `evaluation-results/` directory with a `planning` section alongside the existing match/tailor results, sharing the same acknowledgement mechanism, cost accounting, and pass/fail gates.
