## P0.2 repair handoff, ranked

1. **Human confirmation navigation is blocked after handoff.** Reproducer: `only the separate simulated HUMAN actor confirms in place; frozen target blocks confirmation navigation` at the pinned baseline. Expected: personally initiated submit can reach its exact confirmation URL while the companion remains unable to navigate or submit. Actual: in-place confirmation works, but `/confirmation` navigation is blocked by `TARGET_NAVIGATION_BLOCKED`. Impact: the user may be unable to finish a normal navigational application. Smallest likely scope: a separately authorized, exact-owned human handoff/navigation design and target-guard change with threat review; do not loosen the current guard in P0.1. Regression: preserve companion no-submit and off-target denial while proving human confirmation navigation.
2. **Page-owned transmission needs explicit operator treatment.** Reproducer: mixed native test, one approved URL write triggers fetch/XHR/beacon before Submit. Expected: the user understands that Fill can transmit values immediately and the system reports this limitation accurately. Actual: three local routed effects were observed; no blanket network-free property holds. Impact: applicant values may leave a real page on input. Smallest likely scope: risk disclosure and, if policy requires, bounded transport observability/controls without claiming interception prevents every page effect. Regression: count attempted, fulfilled, failed and submit requests separately.
3. **Indistinguishable repeated questions block whole-form correlation.** Reproducer: async/duplicate test. Expected: safe explicit ambiguity with a recoverable way to work on unambiguous fields where proven. Actual: `AMBIGUOUS_DUPLICATE_FIELD` rejects the entire inspection; removing the duplicate permits inspection. Impact: otherwise useful fields cannot be assisted. Smallest likely scope: conservative section/identity disambiguation or partial manual fallback, subject to protected correlation safety. Regression: reordered duplicates never transfer answer authority.
4. **Dynamic options require a new inspection and can raise operator effort.** Reproducer: async select test. Expected: late option is visible only after a fresh stable inspection; one attempted Fill never gains a new grant. Actual: stale generation is invalidated and reinspection succeeds. This is safe current behavior, not a demonstrated safety defect. Smallest likely scope: clearer waiting/reinspection guidance and narrowly bounded option stabilization if useful. Regression: no guessed option and no second Fill.
5. **Useful eligible coverage remains narrow.** Reproducer: mixed native test and guarded E2E. One professional URL is writable; required contact, file upload, and legal fields remain manual. Expected for a useful trial: meaningful eligible proposals from approved sources with a manageable manual burden. Actual: one test-owned approved URL write; no current vendor-specific useful coverage proof. Smallest likely scope: evaluate source and question policy one field family at a time under separate authorization; retain contact/document/legal boundaries until approved. Regression: no writable type alone creates an answer.
6. **Staged authentication/CAPTCHA is outside current execution.** Reproducer: staged barrier test. Expected: explicit manual/unsupported disposition. Actual: protected inspection stops with `EMPLOYER_AUTH_REQUIRED_UNSUPPORTED`. Smallest likely scope: user-facing fallback and exact-form triage, not an authentication bypass or general Workday adapter. Regression: no credential entry or CAPTCHA action by the companion.

These are P0.2 decisions, not production changes in this branch. The first item is a usability blocker for navigational confirmation, not permission to weaken the frozen target. The second is a disclosed transmission property; whether further mitigation is required needs a policy decision. No result here grants live employer testing or production database access.
